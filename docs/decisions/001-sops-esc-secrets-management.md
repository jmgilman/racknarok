# ADR 001: SOPS + ESC for Secrets Management

## Status

Accepted

## Context

Project Racknarok requires a secrets management solution that:
- Allows secrets to be stored in Git (the single source of truth)
- Provides secure encryption at rest
- Enables safe collaboration (secrets can be committed without exposure)
- Distributes secrets to multiple consumers (Pulumi, Ansible, NixOS VMs)
- Works with CI/CD automation (GitHub Actions)
- Aligns with the "everything as code" philosophy

### Requirements

1. **Git-native**: Secrets must be versioned alongside configuration
2. **Encrypted at rest**: No plaintext secrets in repository
3. **Multi-consumer**: Support Pulumi projects, Ansible, NixOS, and CI
4. **Auditable**: Track who changed what and when
5. **Simple**: Avoid over-engineering for a playground environment
6. **Cost**: Must work within free tier constraints

### Alternatives Considered

**Option 1: Vault Only**
- **Pros**: Industry standard, rich feature set, good security model
- **Cons**:
  - Requires running Vault infrastructure (chicken-and-egg problem)
  - Secrets not in Git (violates single source of truth principle)
  - Complex for initial bootstrap
  - Overkill for single-operator playground

**Option 2: Git-crypt**
- **Pros**: Transparent encryption, simple workflow
- **Cons**:
  - GPG key management complexity
  - Entire repository encrypted or nothing
  - Less flexible than SOPS
  - Doesn't integrate well with ESC

**Option 3: Pulumi ESC Only**
- **Pros**: Integrated with Pulumi stack management
- **Cons**:
  - Secrets not in Git (violates single source of truth)
  - Requires manual ESC management
  - No easy local editing workflow
  - Difficult to audit changes over time

**Option 4: SOPS + ESC (Selected)**
- **Pros**:
  - Git remains source of truth (encrypted secrets committed)
  - SOPS provides file-level encryption with age keys
  - ESC provides runtime distribution mechanism
  - Clear separation: Git = storage, ESC = delivery
  - Easy local workflow (`sops edit`)
  - Age keys simpler than GPG
  - Integrates well with CI/CD
- **Cons**:
  - Two-component solution (more moving parts)
  - Requires SOPS key bootstrap process

## Decision

We will use **SOPS with age encryption** for secrets at rest in Git, and **Pulumi ESC** for secrets distribution at runtime.

### Architecture

```
Git Repository (Source of Truth)
├─ secrets/                         # SOPS-encrypted files
│  ├─ .sops.yaml                    # Encryption config
│  └─ **/*.enc.yaml                 # Encrypted secrets
    ↓
[CI/CD or Orchestrator]
├─ Retrieves SOPS key from ESC
├─ Decrypts secrets
└─ Syncs to ESC environments
    ↓
Pulumi ESC (Distribution)
├─ racknarok/proxmox
├─ racknarok/talos-mgmt
└─ racknarok/services-*
    ↓
Consumers
├─ Pulumi projects (reference ESC envs)
├─ Ansible (orchestrator generates inventory from ESC)
└─ NixOS VMs (systemd services fetch from ESC)
```

### Key Management

- **Age key pair** generated via `scripts/bootstrap-sops.sh`
- **Public key** stored in `secrets/.sops.yaml` (committed to Git)
- **Private key** stored in ESC environment `racknarok/ci`
- **No key rotation** (acceptable for playground environment)

### Workflow

**Editing secrets locally**:
```bash
sops secrets/proxmox/api-tokens.enc.yaml
```

**Syncing to ESC**:
```bash
# Manual
orchestrator.py sync-config

# Automated (CI)
# Triggered on changes to secrets/
```

**Consuming secrets**:
- Pulumi: `const config = pulumi.Config(); config.requireSecret("esc:api_token")`
- Ansible: Inventory generated by orchestrator from ESC
- NixOS: Systemd service fetches from ESC using encrypted token

## Consequences

### Positive

1. **Git as single source of truth**: All secrets versioned, auditable via Git history
2. **Safe collaboration**: Encrypted secrets can be committed and pushed
3. **Simple local workflow**: `sops edit` provides transparent editing
4. **CI/CD friendly**: SOPS key in ESC enables automated sync
5. **Flexible distribution**: ESC provides service-based secret delivery
6. **No infrastructure dependency**: SOPS is CLI tool, no services required
7. **Age simplicity**: Simpler than GPG, modern cryptography

### Negative

1. **Two-component complexity**: Both SOPS and ESC must be understood
2. **Bootstrap dependency**: SOPS key must be manually created and added to ESC
3. **Single key risk**: If SOPS key is lost, all secrets must be re-encrypted
4. **No automatic rotation**: Playground constraint, but limits production readiness

### Mitigation

- **SOPS key backup**: Store private key in secure password manager
- **ESC as backup**: ESC contains decrypted secrets (can recover if SOPS key lost)
- **Documentation**: Clear runbooks for key management and disaster recovery

## Implementation Notes

### Bootstrap Process

1. Generate age key: `scripts/bootstrap-sops.sh`
2. Public key → `secrets/.sops.yaml`
3. Private key → ESC `racknarok/ci` environment
4. Encrypt existing secrets: `sops -e secret.yaml > secret.enc.yaml`

### SOPS Configuration

```yaml
# secrets/.sops.yaml
creation_rules:
  - path_regex: \.enc\.yaml$
    age: age1xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
```

### ESC Environment Structure

```yaml
# racknarok/ci (contains SOPS key)
values:
  sops:
    privateKey:
      fn::secret: "AGE-SECRET-KEY-1XXX..."
```

## Future Considerations

### If scaling beyond playground

- **Key rotation**: Implement age key rotation process
- **Multiple keys**: Use different keys per environment (dev, prod)
- **Vault integration**: Migrate runtime secrets to Vault, keep SOPS for bootstrap
- **Hardware security**: Consider age keys in Yubikey for production

### For now (playground)

- Single age key is sufficient
- No rotation required
- SOPS + ESC provides good balance of security and simplicity
